================================================================================
 TESTING THE GOOGLE MEET CONNECTOR END TO END
 With a personal Google account, on this machine
================================================================================

This is the FIRST time this connector will touch a real Google Meet meeting.
Everything up to the browser has been verified (693 automated tests, including
14 that drive real Chromium). What has NOT been verified is the Meet DOM
selectors, because that needs a live meeting. Expect step 6 to be where trouble
appears, and see section 9 for exactly what to do about it.

Note: `poetry` is not installed on this machine, so every command below uses
`.venv/bin/...` directly.


--------------------------------------------------------------------------------
 0. WHY THIS CONNECTOR NEEDS A BROWSER AT ALL
--------------------------------------------------------------------------------

Zoom and Teams have server-side SDKs that can publish media into a call.
Google has none. Its only real-time media API says so explicitly:

  "All conference media streams are "receive-only". Currently, the Meet Media
   API does not support sending of media from MediaApiClientInterface into a
   conference."
  -- developers.google.com/workspace/meet/media-api/reference/cpp/namespace/meet

So the avatar cannot be a server. It has to be a CLIENT: a real Chromium,
signed in to a real Google account, joining like a person and publishing
through the ordinary getUserMedia path. That is why the "credential" here is a
browser profile on disk rather than a client id and secret.

Full reasoning: docs/design/007-google-meet-connector-architecture.md

--------------------------------------------------------------------------------
 2. THE TWO-ACCOUNT DECISION  (read this, it saves an hour)
--------------------------------------------------------------------------------

  HOST   account = the one that creates and hosts the meeting.
                   You use this in your normal everyday browser.

  AVATAR account = the one Chromium signs in as. This is what appears in the
                   meeting as a participant.

OPTION A - two different accounts  (RECOMMENDED)

  Use your personal Google account as HOST, and a second Google account as the
  AVATAR. Create a free one if you do not have a spare.

  What happens: the avatar lands in "Asking to join" and YOU click Admit. That
  is the realistic production flow, and it exercises the lobby path — the piece
  most likely to behave differently from what the code assumes.

OPTION B - the same account for both

  Works, and is fine for a first smoke test. Meet normally lets the second
  session straight in with no lobby, because it recognises the account.

  Downsides: two tiles with the same name, and you never exercise the lobby.

Either way: DO NOT sign the Chromium profile in as an account you care about
losing access to. Automated sign-ins can get an account challenged or blocked.


--------------------------------------------------------------------------------
 3. SIGN THE BROWSER PROFILE IN  (once, ~2 minutes)
--------------------------------------------------------------------------------

The service CANNOT do this for you. The join flow checks the Google session
before it opens the meeting — on purpose, so an unauthenticated profile gives a
clear error instead of a mysterious timeout 20 seconds later. The side effect is
that a first run fails before you could type anything. Hence a separate tool:

    .venv/bin/python tools/meet_signin.py

A Chromium window opens on accounts.google.com.

  1. Sign in as the AVATAR account.
  2. Complete 2-step verification if asked.
  3. LEAVE THE BROWSER OPEN. The tool polls and detects success itself, then
     closes the browser cleanly so the cookie store is flushed to disk.

You are looking for:

    OK - signed in as a***@gmail.com
      session saved to /Users/dev/work/meeting-connectors/.meet/profile

Check it any time without changing anything:

    .venv/bin/python tools/meet_signin.py --check

Notes
  - The profile lives at .meet/profile and is gitignored. It contains a LIVE
    Google session cookie. Do not commit it, do not copy it around.
  - It is a TEMPLATE. Each session runs on a throwaway clone, so sessions cannot
    corrupt each other's login and a crash can never cost you the sign-in.
  - You should not need this tool again unless Google expires the session.

If Google says "This browser or app may not be secure":
  Sign in on that same profile using a normal-looking flow — open the Chromium
  window the tool launched, go to gmail.com, and sign in there instead. Once the
  session exists in the profile, the connector never touches sign-in again.


--------------------------------------------------------------------------------
 4. START THE SERVICE
--------------------------------------------------------------------------------

Terminal 1 - your mock avatar (already running on 8100). Leave it.

Terminal 2 - the bridge:

    cd /Users/dev/work/meeting-connectors
    .venv/bin/uvicorn src.main:app --port 8000 --log-level info

Expected on startup:

    connectors.registered   platforms=['google_meet', 'zoom']
    service.startup         app=meeting-connectors env=local

If you see platforms=['zoom'] only, MC_GOOGLE_MEET__PROFILE_DIR is not being
read — check you are running from the repo root so .env is found.


--------------------------------------------------------------------------------
 5. CREATE AND JOIN THE MEETING  (as HOST, in your normal browser)
--------------------------------------------------------------------------------

  1. Go to https://meet.google.com
  2. "New meeting" -> "Start an instant meeting"
  3. **JOIN IT YOURSELF AND STAY IN IT.**

     This is not optional. A personal Meet link is not a live conference until
     the host is in it. If you start the avatar first it will sit in a lobby
     that nobody can admit it from, and time out after 300s.

  4. Copy the meeting code from the URL. It looks like:

         https://meet.google.com/abc-defg-hij
                                 ^^^^^^^^^^^^  <- this part

  5. USE HEADPHONES, or mute your own mic.

     The avatar publishes real audio into the call. Your laptop speakers +
     laptop mic will loop it straight back in. EchoGuard's speaking gate
     handles the software path, but it cannot do anything about a room.


--------------------------------------------------------------------------------
 6. PUT THE AVATAR IN THE MEETING
--------------------------------------------------------------------------------

Terminal 3:

    curl -X POST localhost:8000/sessions \
      -H 'content-type: application/json' \
      -d '{"platform": "google_meet", "meeting_number": "abc-defg-hij"}'

  (substitute your real code; a full https://meet.google.com/... link also
   works, in either "meeting_number" or "meeting_url")

Because MC_GOOGLE_MEET__HEADLESS=false, a Chromium window will open and you can
WATCH the whole join. Keep an eye on both that window and Terminal 2.

If you chose OPTION A (two accounts): switch to your HOST browser and click
**Admit** when the notification appears. You have 300 seconds.

The response is a 202 with a session id. Keep it:

    {"session_id": "ses_...", "state": "joining", ...}


--------------------------------------------------------------------------------
 7. WHAT SUCCESS LOOKS LIKE
--------------------------------------------------------------------------------

Terminal 2, roughly in this order:

    meet_bridge.listening          endpoint=ws://127.0.0.1:5xxxx/bridge/<token>
    meet_profile.cloned            files=4
    meet_browser.launched          headless=False args=15
    meet_bridge.page_connected     generation=1
    meet_auth.signed_in            account=a***@gmail.com
    meet_join.navigating           target=abc-defg-hij
    meet_join.in_lobby                              <- only with two accounts
    meet_join.joined               lobby_wait_s=12.4
    meet_controls.unmuted
    meet_controls.camera_on
    meet_bridge.joined             capture_hz=16000 publish_hz=48000
                                   audio_published=True video_published=True
    router.first_fragment          <- your mock avatar's media arriving
    meet_bridge.roster             participants=2 others=1

THE TWO LINES THAT MATTER MOST are meet_controls.unmuted and
meet_controls.camera_on. Meet does not publish tracks it was handed until it is
told to, and NOTHING else in the system can observe that it wasn't. A browser
that joined muted looks perfectly healthy at every layer and is silent in the
meeting.

In the HOST browser you should see:
  - a new participant named after the AVATAR account
  - its tile showing your mock avatar's video (not a grey box, not an initial)
  - audio from it

Check health any time:

    curl -s localhost:8000/sessions/ses_... | python3 -m json.tool

Look for state "active" and, under components, google_meet_publisher with a
detail like "audio=812 video=406 dropped_audio=0 dropped_video=0". Counts
climbing = media genuinely flowing. audio=0 while the bridge is healthy means
Meet is holding a track it was never told to publish.


--------------------------------------------------------------------------------
 8. STOP
--------------------------------------------------------------------------------

    curl -X DELETE localhost:8000/sessions/ses_...

This clicks Leave before closing the browser, so the avatar disappears from the
roster immediately rather than lingering as a frozen tile for minutes.

Ctrl-C on uvicorn also drains every live session, so a redeploy never leaves a
bot sitting in someone's meeting.


--------------------------------------------------------------------------------
 9. IF THE JOIN FAILS  (most likely: Meet changed its UI)
--------------------------------------------------------------------------------

The selectors in src/connectors/google_meet/automation/selectors.py are the only
part of this connector that has never been checked against live Meet. They are
deliberately isolated in one file, with several candidates per concept, so a
Meet rename is a one-line fix rather than a rewrite.

If you see:

    JoinTimeoutError: no join button appeared within 120s;
    Meet's pre-join screen may have changed (see automation/selectors.py)

then with HEADLESS=false the Chromium window is still open at the failure point.
Do this:

  1. In that Chromium window, right-click the real "Join now" / "Ask to join"
     button -> Inspect.
  2. Copy its aria-label, or the text inside its <span>.
  3. Add a candidate to MeetSelectors.join_button in selectors.py. Old and new
     can coexist — the code tries each in order, so nothing breaks.

Same procedure for in_call, leave, mute_toggle, camera_on_toggle. Every field is
a tuple; append, don't replace.

Send me the failing log line plus what you saw in Inspect and I will patch it.

FULL ERROR REFERENCE
--------------------
  no connector registered for platform 'google_meet'
      MC_GOOGLE_MEET__PROFILE_DIR unset, or you are not running from the repo
      root. Check startup for connectors.google_meet_not_registered.

  the Chromium profile is not signed in to Google
      Step 3. The message repeats the fix. Fatal by design: retrying a sign-in
      Google has already challenged makes things worse.

  Google is challenging this browser
      2-step verification or device verification. A human must complete it once,
      headed. See the note at the end of step 3.

  google meet refused admission: the host denied the request
      You (or a co-host) clicked Deny. TERMINAL ON PURPOSE — the connector will
      NOT retry. An account that repeatedly asks into a meeting it was refused
      from looks like abuse, and losing the account breaks everything.

  the avatar was removed from the meeting
      Same, same reason.

  nobody admitted the avatar within 300s in the lobby
      You missed the Admit prompt. Recoverable — just try again. Raise
      MC_GOOGLE_MEET__LOBBY_TIMEOUT_S if you need longer.

  the Chromium page did not connect to the bridge within 60s
      The injected script never ran. Distinct from a join timeout: the browser
      started but never reached Python. Should not happen — the Local Network
      Access flag that causes this is already set — but if it does, check that
      --disable-features=LocalNetworkAccessChecks is still in the launched args.

  the page built a 48000 Hz capture context but the avatar contract requires 16000
      A stale js/bridge.js. Fatal rather than resampled: the alternative is a
      chipmunk avatar that looks like an avatar-service bug.

  no conference audio for 45s with 1 other participant(s) present
      The media watchdog. The browser is alive but the capture graph has lost
      its inputs or been suspended — the one failure every other check reports
      as healthy. Are you actually speaking? It only fires when someone else is
      in the call.

  Avatar joins, is visible, but never speaks
      Your mock avatar is not sending, or is sending non-fragmented MP4. Check
      Terminal 2 for router.first_fragment — if absent, nothing came back from
      8100. The stream must be fMP4
      (-movflags +frag_keyframe+empty_moov+default_base_moof).

  Avatar tile is a grey box
      Video is flowing (grey is the canvas's initial fill) but no decoded frames
      reached it. Check for ffmpeg errors and for router.first_fragment.

  Renderer keeps crashing / rejoins climbing
      Memory. Not likely on a Mac with one session; matters in a container,
      where /dev/shm must be larger than Docker's 64 MB default.


--------------------------------------------------------------------------------
 10. AFTER IT WORKS
--------------------------------------------------------------------------------

  - Set MC_GOOGLE_MEET__HEADLESS=true for anything unattended.
  - Two concurrent sessions are supported: each gets a cloned profile, and
    BRIDGE_PORT=0 means their loopback servers cannot collide. Try two meetings
    at once to confirm.
  - Still open, and NOT Meet-specific: AvatarClient.reconnect() is never called,
    and the avatar transport does not reopen its queues after a close. So if
    your mock avatar restarts mid-meeting, that session's audio stops for good.
    Restart the session as a workaround. Documented in docs/design/007 §7.
  - The Dockerfile has no Chromium yet, so this is a run-it-locally setup only.
